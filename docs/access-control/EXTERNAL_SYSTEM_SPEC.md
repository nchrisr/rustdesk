# RustDesk Access-Control Backend — Implementation Spec

This document specifies the HTTP API and business rules that an external system
must implement to act as the authorization and session-tracking backend for a
customized RustDesk build (**RustDesk-Velour**; its implementation plan is in
`VELOUR_PLAN.md`, which is not needed to build the backend). It is written to be self-contained: an engineer (or
an AI assistant) should be able to implement the backend from this document
alone.

## 1. Background

RustDesk is a remote-desktop tool. Every RustDesk installation has a stable
9-digit **RustDesk ID**. A person connects *from* one installation (the
**peer**) *to* another (the **device**).

The customized RustDesk build adds an access-control layer. Instead of deciding
on its own who may connect, the **device** asks this backend. The backend
already holds the organization's users and roles; each user is linked to the
remote-desktop installation(s) they connect from by a **remote application ID**.

### Application-neutral IDs

The backend must not assume RustDesk. It has historically stored AnyDesk IDs
and may store IDs from other tools later. Every ID is therefore stored and
looked up as a pair `(app, remote_id)`, where `app` is a short lowercase
identifier of the remote-desktop application (`"rustdesk"`, `"anydesk"`, …)
and `remote_id` is that application's own ID string. RustDesk always sends
`"app": "rustdesk"` in every request. Uniqueness is on the pair, never on
`remote_id` alone. In this document, `peer_id` and `device_id` are
`remote_id` values within the request's `app` namespace.

The backend has three jobs:

1. **Authorize** incoming connections (who is this, what role, may they connect
   right now, how long may they stay).
2. **Receive session events** (start, heartbeat, end, denied) and answer each
   heartbeat with the remaining allowed time, or an instruction to stop.
3. **Expose active sessions** so an Admin's RustDesk app can list and watch
   them.

Everything else (user management UI, schedules, quotas, dashboards) is internal
to the backend and is described as requirements, not as endpoints.

### Roles

| Role | Connect to which devices | Concurrency | Schedules / quotas |
|---|---|---|---|
| `admin` | Any device, any time | Never blocked | Exempt |
| `manager` | Only devices assigned to them | Never blocked | Apply if configured (per device) |
| `user` | Only devices assigned to them (see `users_require_assignment`) | Blocked if another `user` is connected to that device | Apply if configured (per device) |

The "one `user` at a time" rule is enforced by the device itself (it knows in
real time who is connected). The backend may also enforce it using the
`connected` list in the authorize request, but must not rely on it being
perfectly current.

### Personal tokens

Every user has a **personal token**: a random secret (≥ 32 bytes, URL-safe
base64 or hex) generated by the backend, shown to the user once, and stored
only as a hash (bcrypt/argon2/SHA-256+pepper — any is fine, but comparison must
be constant-time). The user pastes it into their RustDesk settings. On every
connection the peer's RustDesk app sends its ID and this token; the device
forwards both to the backend. The backend approves only if the token matches
the user who owns the `(app, remote_id)` pair sent. This prevents a peer
from claiming someone else's ID.

Revoking a user = deleting or regenerating their token (and/or setting
`active = false`). RustDesk needs no update.

## 2. Data model (minimum)

```
users
  id              PK
  name            text
  role            enum(admin, manager, user)
  token_hash      text, nullable
  timezone        text (IANA, e.g. "America/Toronto"), default = system tz
  active          bool

user_remote_ids                            -- installations a user connects FROM
  user_id         FK users
  app             text                     -- "rustdesk", "anydesk", ...
  remote_id       text
  UNIQUE (app, remote_id)                  -- one owner per ID; a user may have several rows

devices                                    -- machines that can be connected TO
  id              PK
  app             text
  remote_id       text
  name            text
  UNIQUE (app, remote_id)

device_api_keys                            -- credentials devices use to call this API
  id              PK
  key_hash        text
  device_id       FK devices, nullable     -- if set, the request's (app, device_id) must match
  active          bool

device_assignments                         -- which managers/users may reach which devices
  user_id         FK users
  device_id       FK devices

schedules                                  -- allowed windows, evaluated in users.timezone
  user_id         FK users
  device_id       FK devices, nullable     -- null = default for devices without their own rows
  weekday         0..6 (0 = Monday)
  start_time      time (local)
  end_time        time (local)             -- may be past midnight; treat as next day

quotas                                     -- max connected seconds per calendar period
  user_id         FK users
  device_id       FK devices, nullable     -- null = default for devices without their own rows
  period          enum(day, week, month)
  max_seconds     int

sessions                                   -- fed entirely by events
  session_id      uuid PK                  -- generated by the device
  app             text                     -- "rustdesk"
  user_id         FK users, nullable       -- null for auth_denied with unknown peer
  peer_remote_id  text
  device_remote_id  text
  role            text
  conn_type       enum(remote, file_transfer, terminal, port_forward, view_camera)
  monitoring      bool                     -- admin watching in view-only mode
  offline_authorized  bool                 -- device used its local cache (backend was unreachable)
  status          enum(active, stale, ended)
  started_at      timestamptz
  last_heartbeat_at  timestamptz
  ended_at        timestamptz, nullable
  end_reason      text, nullable
  elapsed_seconds int                      -- last value reported by the device

processed_events                           -- for idempotency
  event_id        uuid PK
  received_at     timestamptz
```

Settings (global): `users_require_assignment` (bool, default `true`),
`heartbeat_interval_seconds` (default 30, informational), `stale_after_seconds`
(default 90 = 3 missed heartbeats), `lost_after_seconds` (default 300).

## 3. Transport and authentication

* HTTPS only. All bodies are JSON (`Content-Type: application/json`).
* Every request from a device carries `Authorization: Bearer <device_api_key>`.
  Reject with `401` if the key is unknown or inactive. If the key row is bound
  to a device, reject with `403` if the body's `(app, device_id)` differs.
* Every request body carries `"app"` (see §1). Reject with `400` if missing.
* **Latency budget: respond within 2 seconds.** The device gives up after 5
  seconds and treats the request as "backend unreachable".
* Timestamps are RFC 3339 UTC strings (`2026-09-11T14:03:00Z`).
* Unknown JSON fields must be ignored (forward compatibility).

## 4. Endpoints

### 4.1 `POST /v1/authorize` — decide whether a connection may proceed

Called by the device once per incoming connection, before the session starts.

Request:
```json
{
  "app": "rustdesk",
  "peer_id": "123456789",
  "peer_token": "k3Jd...",
  "device_id": "987654321",
  "conn_type": "remote",
  "monitoring": false,
  "connected": [
    { "peer_id": "555555555", "role": "user", "session_id": "…" }
  ]
}
```
* `conn_type`: one of `remote`, `file_transfer`, `terminal`, `port_forward`,
  `view_camera`.
* `monitoring`: `true` when an Admin is opening a view-only tile from the
  monitor wall. Such sessions must not count toward quotas or the "one user"
  rule.
* `connected`: peers currently connected to this device (may be empty). Best
  effort; do not treat as authoritative.

Decision procedure (stop at the first failure):

1. Find `user_remote_ids` row where `(app, remote_id) = (app, peer_id)` and
   its user. None → **404** `{"error": "unknown_peer"}`. Resolve `device_id`
   the same way against `devices`; an unknown device → **404**
   `{"error": "unknown_device"}`.
2. `active` is false, or `token_hash` is null, or token does not match →
   **200** `{"allowed": false, "reason_code": "invalid_token", "reason": "Invalid access token."}`.
   (Do not distinguish "wrong token" from "inactive user" to the caller.)
3. Role `admin` → allowed.
4. Role `manager` → allowed only if a `device_assignments` row exists for this
   device. Else `reason_code: "not_assigned"`.
5. Role `user` → if `users_require_assignment`, require an assignment row as
   for managers. Then, if `connected` contains another entry with role `user`
   and `monitoring` is false → `reason_code: "user_already_connected"`. (The
   device enforces this too; this is a courtesy check.)
6. If `monitoring` is false: check schedule and quotas (see §5). Outside the
   window → `reason_code: "outside_schedule"`. Quota exhausted →
   `reason_code: "quota_exhausted"`.
7. Otherwise allowed.

Success response (`200`):
```json
{
  "allowed": true,
  "user_id": "u_42",
  "display_name": "Ada Lovelace",
  "role": "manager",
  "remaining_seconds": 14400
}
```
* `remaining_seconds`: see §5.3. Omit or `null` when unlimited. The device uses
  it to seed the on-screen countdown before the first heartbeat.

Denial response (`200`):
```json
{
  "allowed": false,
  "reason_code": "outside_schedule",
  "reason": "You may connect Mon–Fri 09:00–17:00 (America/Toronto)."
}
```
`reason` is shown verbatim to the person trying to connect. Keep it short and
actionable. `reason_code` values: `invalid_token`, `not_assigned`,
`user_already_connected`, `outside_schedule`, `quota_exhausted`, `other`.

Every authorize call, allowed or denied, should be logged. Denials are also
reported by the device as `auth_denied` events (§4.2), but only when the device
itself refused; backend denials are already known to the backend.

### 4.2 `POST /v1/events` — session lifecycle events

The device sends one event per request. All events share an envelope:

```json
{
  "event": "session_start",
  "event_id": "5c1d…",
  "ts": "2026-09-11T14:03:00Z",
  "session": {
    "session_id": "9f2a…",
    "app": "rustdesk",
    "device_id": "987654321",
    "device_name": "Lab-PC-3",
    "peer_id": "123456789",
    "peer_name": "Ada's laptop",
    "user_id": "u_42",
    "role": "manager",
    "conn_type": "remote",
    "monitoring": false,
    "offline_authorized": false,
    "started_at": "2026-09-11T14:03:00Z",
    "elapsed_seconds": 0
  },
  "data": {}
}
```

* `event_id` is unique per event. **Requests are retried; the backend must be
  idempotent**: if `event_id` was already processed, return `200` with the same
  response as before and change nothing.
* `session_id` is a UUID generated by the device when the session is approved.
  It is the key for everything about that session.
* `offline_authorized`: the backend was unreachable at connect time and the
  device allowed the connection from its local cache of a previous approval.
  The backend should create the session as usual and apply quota rules on the
  next heartbeat (which may result in `continue: false`).
* `user_id` may be absent on `auth_denied` for unknown peers.

Event types and `data` payloads:

| `event` | When | `data` | Response |
|---|---|---|---|
| `session_start` | Once, after approval | `{}` | `{ "ok": true }` |
| `heartbeat` | Every 30 s while active | `{}` | see below |
| `session_end` | Once, on close | `{ "reason": "peer_disconnected" \| "device_closed" \| "network_lost" \| "backend_stop" \| "access_control_disabled" \| "other", "detail": "…" }` | `{ "ok": true }` |
| `auth_denied` | Device refused a connection itself | `{ "reason_code": "no_token" \| "not_configured" \| "backend_unreachable" \| "user_already_connected" \| "cache_expired", "reason": "…" }` | `{ "ok": true }` |

Processing rules:

* `session_start`: upsert `sessions` with `status = active`. If a `heartbeat`
  arrives for an unknown `session_id` (start was delayed by retries), create
  the session from the envelope rather than rejecting it.
* `heartbeat`: update `last_heartbeat_at` and `elapsed_seconds`. Return:
  ```json
  { "continue": true, "remaining_seconds": 12570 }
  ```
  or, to end the session:
  ```json
  { "continue": false, "reason": "Your weekly limit of 10 hours has been reached." }
  ```
  The device closes the session and shows `reason` to the person. Send
  `continue: false` **only when `remaining_seconds` would be ≤ 0** (or the
  user was deactivated / an admin ended the session manually). The countdown
  on the person's screen is driven by `remaining_seconds`, so cut-offs must
  never come as a surprise. `remaining_seconds` omitted/`null` = unlimited.
  Heartbeats for `monitoring: true` sessions always get `continue: true` unless
  the admin's user was deactivated.
* `session_end`: set `status = ended`, `ended_at`, `end_reason`, final
  `elapsed_seconds`. Reason `access_control_disabled` means the device's owner
  turned the feature off; the session itself may still be running unreported.
* Events can arrive out of order or duplicated. Never move a session from
  `ended` back to `active`. Use `ts` to ignore stale updates.
* **Stale detection** (background job): a session with no heartbeat for
  `stale_after_seconds` becomes `stale`; after `lost_after_seconds` with no
  `session_end`, mark it `ended` with `end_reason = "lost"`, using
  `last_heartbeat_at` as `ended_at`. If a `session_end` arrives later, apply
  its values.

Response codes: `200` on success (including duplicates), `400` for malformed
JSON, `401/403` for auth. Do not return `4xx` for unknown `session_id`; create
it (see above).

### 4.3 `GET /v1/sessions/active` — list live sessions (Admin monitor wall)

Called by an Admin's RustDesk app. Authenticated with the Admin's personal
token: `Authorization: Bearer <personal_token>`. Reject with `401` if the
token does not belong to an active user with role `admin`.

Query params: `app` and `device_id` (optional filters).

Response:
```json
{
  "sessions": [
    {
      "session_id": "9f2a…",
      "app": "rustdesk",
      "device_id": "987654321",
      "device_name": "Lab-PC-3",
      "peer_id": "123456789",
      "user_id": "u_42",
      "display_name": "Ada Lovelace",
      "role": "manager",
      "conn_type": "remote",
      "status": "active",
      "started_at": "2026-09-11T14:03:00Z",
      "elapsed_seconds": 1830,
      "remaining_seconds": 12570
    }
  ]
}
```
Exclude `monitoring: true` sessions and `ended` sessions. Include `stale`
sessions with `status: "stale"` so the Admin can see connections that may have
dropped.

## 5. Business rules

### 5.1 Schedules (per user, per device)

Schedules and quotas are defined for a **user + device pair**, so the same
person can have different limits on different machines.

* **Row selection:** for a request involving `device_id`, use the user's
  `schedules` rows whose `device_id` is the resolved device. If there are none,
  fall back to the user's rows with `device_id = null` (the default
  set). Device-specific rows fully replace the default set; they are not
  merged.
* If the selected set is empty, the user is allowed at any time on that device.
* Otherwise the user is allowed only when the current time (in
  `users.timezone`) falls within at least one selected row. Windows crossing
  midnight (e.g. 22:00–02:00) are valid.
* Admins are exempt regardless of rows.

### 5.2 Quotas (per user, per device)

* **Row selection:** same rule as schedules — device-specific rows for this
  `device_id` if any exist, otherwise the user's default rows
  (`device_id = null`).
* Usage for a period = sum of `elapsed_seconds` over that user's sessions **on
  that device** (excluding `monitoring` sessions) whose `started_at` falls in
  the period. `active`/`stale` sessions count their current `elapsed_seconds`.
  Time spent on other devices never counts against this device's quota.
* Periods are calendar-based in the user's timezone: `day` = today, `week` =
  Monday 00:00 to next Monday, `month` = calendar month.
* A user may have several quota rows for the same device (e.g. 4 h/day and
  15 h/week); all apply.
* Concurrent sessions by the same user on the same device each count
  separately. (Document this in the admin UI; it is a deliberate
  simplification.)
* Admins are exempt.

### 5.3 `remaining_seconds`

Computed identically in `/v1/authorize` and heartbeat responses, using the
schedule and quota rows selected for this user + device:

```
remaining = min(
  for each selected quota row:   max_seconds - usage_in_period_on_this_device,
  if selected schedules exist:   seconds until the current window's end_time
)
```
If no quota rows and no schedules apply → `null` (unlimited). Never negative;
clamp to 0. If `remaining == 0` on a heartbeat, respond `continue: false`.

Because this is recomputed every 30 seconds, an admin who extends a quota or
schedule sees the change reflected on the user's screen within one heartbeat.

### 5.4 Manual termination

The admin UI should offer "End session" on any active session. Implement it by
flagging the session (e.g. `terminate_requested = true`); the next heartbeat
gets `{ "continue": false, "reason": "Session ended by administrator." }`.
There is no push channel to the device; termination takes up to one heartbeat
interval.

## 6. Admin UI requirements (internal, not an API contract)

* Create/edit users: name, role, timezone, active flag, and their remote
  application IDs (one or more `(app, remote_id)` pairs).
* Generate / regenerate a user's personal token; show it once.
* Manage devices (`(app, remote_id)`, name) and device API keys (generate,
  revoke).
* Assign users/managers to devices.
* Edit schedules and quotas per user, with a default set plus optional
  per-device overrides.
* Dashboard: active sessions (live), session history with durations per user
  and device, denied attempts. "End session" button.
* Warn when a user has no `rustdesk` remote ID: they will get `unknown_peer`
  when they try to connect, and the RustDesk client tells them to ask an admin
  to verify the ID on file.

## 7. Security checklist

* Store token and API-key hashes only; compare in constant time.
* Rate-limit `/v1/authorize` per device key and per `peer_id` (e.g. 10/min) to
  slow token guessing.
* Log every authorize decision and every `auth_denied` event with IPs.
* Do not echo the token back in any response or log.
* All endpoints HTTPS; reject plain HTTP.

## 8. Test scenarios (acceptance)

Authorize:
1. Unknown `(app, peer_id)` → 404 `unknown_peer`. A `peer_id` that exists
   only under `app: "anydesk"` is unknown for `app: "rustdesk"`.
1b. Missing `app` → 400. Unknown `(app, device_id)` → 404 `unknown_device`.
2. Known peer, wrong token → `allowed: false`, `invalid_token`.
3. Inactive user, correct token → `allowed: false`, `invalid_token`.
4. Admin, any device, any time → allowed, `remaining_seconds` null.
5. Manager, assigned device → allowed. Unassigned → `not_assigned`.
6. User, assigned, no one connected → allowed. Another `user` in `connected` →
   `user_already_connected`. Only an `admin` in `connected` → allowed.
7. User with schedule Mon–Fri 09:00–17:00 at Saturday 10:00 (user tz) →
   `outside_schedule`. At Monday 16:30 → allowed with `remaining_seconds` = 1800.
8. User with 1 h/day quota on device X and 50 min used today on X → allowed,
   `remaining_seconds` = 600. With 60 min used → `quota_exhausted`.
8b. Same user, 50 min used today on device X, connecting to device Y with a
    default 1 h/day quota and no usage on Y → `remaining_seconds` = 3600.
8c. User has a default schedule 09:00–17:00 and a device-specific schedule for
    device Z of 18:00–22:00. At 10:00: device X → allowed; device Z →
    `outside_schedule`.
9. `monitoring: true` for an admin → allowed, ignores schedule/quota/connected.
10. Bad/missing API key → 401. Key bound to device A, body says device B → 403.

Events:
11. `session_start` creates an active session; a duplicate `event_id` is a
    no-op returning 200.
12. `heartbeat` before `session_start` (out of order) creates the session.
13. `heartbeat` updates `elapsed_seconds` and returns decreasing
    `remaining_seconds`; when it reaches 0 the response is `continue: false`.
14. `session_end` marks ended; a later `heartbeat` with older `ts` does not
    reactivate it.
15. No heartbeat for 90 s → `stale`; for 300 s → `ended` with reason `lost`.
16. Admin "End session" → next heartbeat gets `continue: false`.
17. `offline_authorized: true` session over quota → first heartbeat returns
    `continue: false`.

Active sessions:
18. Admin token lists active + stale sessions, excludes ended and monitoring.
19. Non-admin token → 401.

## 9. Values the RustDesk side needs from you

When the backend is deployed, each RustDesk device will be configured with:
* the base URL (e.g. `https://access.example.com`),
* a device API key.

Each user will be given their personal token.
